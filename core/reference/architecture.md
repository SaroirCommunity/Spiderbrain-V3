# Spiderbrain architecture

The complete specification of a spiderbrain folder: what every file is, which
files are generated, which are curated, and the data model underneath.

## The cardinal rule: generated vs curated

Every file in a spiderbrain is exactly one of two kinds. Mixing them is the
mistake that makes second-brain systems rot.

- **GENERATED** - derived from the project's filesystem. Disposable. Rewritten
  on every build/consolidate. Carries a `<!-- GENERATED by spiderbrain -->`
  banner. **Never hand-edit one** - your edit is lost on the next rebuild.
- **CURATED** - written by a human (or an agent acting deliberately). Precious.
  Holds judgement and history that no tool can re-derive. Written **once** as a
  stub by `build-brain.mjs`, then owned by you. A rebuild **never** touches it.

Derived data cannot rot, because it is always recomputed from reality. Curated
data is where the irreplaceable knowledge lives, so it is never destroyed.

## Folder layout

```
<project>-spiderbrain/
  spiderbrain.config.json   CURATED   prey, project path, clusters, extra edges
  webscore-overrides.json   CURATED   per-node webscore + role judgements
  SPIDERBRAIN.md            CURATED   the brain's own readme + upkeep rules
  movemap.md                CURATED   permanent deploy log (append-only)
  synganglion.json          GENERATED the master graph - single source of graph truth
  spideyorder.md            GENERATED every node ranked by webscore
  spideymove.md             GENERATED every node ranked by recency
  molt-report.md            GENERATED the latest drift audit
  cephalothorax/            volatile  session hot-file journals (SESSION-*.jsonl)
  <cluster>/                one folder per feature cluster:
    webmap.md               GENERATED the cluster's content map - its top-8 legs
    rules.md                CURATED   conventions and invariants
    config.md               CURATED   configuration facts, env, services
    changelog.md            CURATED   what changed and why (append-only)
```

`database/` additionally holds a curated `fields.md` - the per-field reference.

## synganglion.json - the graph

The master graph. GENERATED; `build-brain.mjs` / `consolidate.mjs` are the only
writers. Shape:

```jsonc
{
  "spiderbrain": 1,
  "generatedAt": "<iso>",
  "sourceHash": "<12 hex>",        // hash of all file paths + mtimes
  "prey": "<the goal>",
  "displayK": 8,                   // how many "legs" a webmap shows
  "stats": { "nodeCount", "edgeCount", "clusterCount" },
  "clusters": {
    "<name>": { "title", "webscore", "nodeCount", "topNodes": [ids] }
  },
  "nodes": {
    "<id>": {
      "cluster": "<name>",
      "kind": "code|style|sql|html|config|content|table|field",
      "role": "<one line - what this is>",
      "webscore": 9.9,             // effective score (override, else auto)
      "webscoreAuto": 3.1,         // derived baseline (fan-in based)
      "dependsOn":    [ids],       // out-edges, webscore-sorted
      "dependedOnBy": [ids],       // in-edges (fan-in) - UNCAPPED
      "dependencyChangedAt": [ { "dep": id, "at": iso } ],
      "lastChangedAt": "<iso>",
      "fileCount": 1
    }
  },
  "edges": [ ["from","to"], ... ]  // canonical directed list; "from" depends on "to"
}
```

A **node id** is a project-relative POSIX path (`app/worker.js`), a collapsed
directory (`content/blog-drafts/01-ai/`), or a DB node (`db:leads`,
`db:leads.email`).

### Edges and direction

`edges` is the single canonical store: `["from","to"]` means **from depends on
to**. `dependsOn` and `dependedOnBy` are both derived from it on every build -
one source, two indexes, never hand-maintained in two directions.

Edges come from three places: scanned `import`/`require`/dynamic-import
specifiers; DB structure (field→table, FK pairs); and `extraEdges` in the
config - the **runtime edges a static scan cannot see** (a browser `fetch()` to
a Worker route, code that queries a table). Without `extraEdges` the graph of a
web app is wrong.

### Propagation direction

When file **X** changes, the nodes at risk are the ones that **depend on X**
(its `dependedOnBy` / fan-in) - "a thing I rely on moved; I may be stale."
`dependencyChangedAt` records this **on the dependent**, derived from mtimes: if
a dependency changed after this node last did, it is listed. Fan-in is therefore
never capped - a file with 200 dependents keeps all 200, because that count *is*
the blast-radius signal.

### The number 8

`displayK` (default 8 - the spider's legs) is a **display** parameter only. The
graph stores every real edge. A `webmap.md` *shows* the cluster's 8 highest-
webscore nodes and each node's 8 strongest links. Storage is complete; display
is truncated. Never cap stored edges.

## Webscore

`0.0–10.0` decimal. **If this node were corrupted, how much of the user
experience breaks - weighted toward the prey.** Two values per node:

- `webscoreAuto` - derived baseline, mostly a function of fan-in. Honest but
  blind to runtime importance (an HTTP entrypoint has near-zero import fan-in).
- `webscore` - the effective score: the curated override from
  `webscore-overrides.json` if present, else `webscoreAuto`.

Large divergence between the two is **expected and fine** for runtime
entrypoints - `molt.mjs` reports it as informational, never as drift. See
`webscore-rubric.md`.

## Clusters

A cluster is a feature - a "nerve cell cluster". Every node belongs to exactly
one, assigned by the first matching rule in `config.clusterRules` (ordered
specific → general; the last rule is usually a `**` catch-all). A cluster has
its own **cluster webscore** - the feature's importance to the whole project,
set in `config.clusterWebscores` (e.g. a blog is one feature among many, so it
scores low even though the project as a whole is critical).

## Collapsed directories

`config.collapseDirs` (glob patterns) makes a whole directory a single
**content node** instead of one node per file - used for large bodies of near-
identical content (e.g. blog markdown) that have no import graph. Git remains
their per-file history; the brain just records the directory, its file count,
and its edges to the rendering pipeline.

## Scaling

A single `synganglion.json` is fine into the low thousands of nodes. Past that,
the format shards cleanly per cluster (each cluster folder holds its own graph
fragment, with a thin top-level index of cross-cluster edges) - the cluster
structure already exists, so sharding is a change to the writers, not the model.
Build it only when one file actually hurts (parse time, or git merge conflicts
on a machine-generated file) - not on spec.

## The reflex arc

A corruption is a domino: one bad node fells its dependents, fast. The reflex
arc makes that cascade **observable, located, and reversible** - three organs
working as one reflex.

### The polar cell grid

Every node has a polar coordinate. **Ring** = webscore band (`config.rings`,
default `[8.5, 7, 5, 3]` → ring 0 hub … ring 4 rim). **Sector** = cluster. The
**cell** `r<ring>:<sector>` is the error boundary - a clean partition, every
node in exactly one cell. A node also carries `contentHash` and `blastRadius`
(its transitive dependent count); the graph carries top-level `cells` + `rings`.

### The nerve net - `lib/nervenet.mjs`

`cascade(graph, badIds)` propagates a fault along **dependent** edges (BFS) and
returns the blast radius, the `wavefront` (count per shell - the shockwave),
the cells tripped in trip-order, and the **origin**: the topological root, the
bad node depending on no other bad node. The first domino, found by graph not
by clock. `cascade.mjs --inject` simulates it; build and molt call the same
function on a real corruption. One engine, test mode and live defence.

### The dragline - `lib/dragline.mjs`

Before any build or consolidate, `anchorDragline()` snapshots every curated
file into `.dragline/<timestamp>/` (last 10 kept). A curated file that fails to
parse is **never** overwritten with defaults - it is quarantined to
`<name>.fouled-<ts>` and restored from the dragline. This is also the brain's
only backup of the curated layer.

### Two clocks

Recency (`lastChangedAt`, `spideymove`) uses the **git commit time** - immune
to the mtime reset a `clone` or `checkout` inflicts; mtime is only the fallback.
Fault-origin uses **topology** - no clock at all. Different jobs, different
instruments.

### Scale note

`webscoreAuto` is the transitive-dependent count, computed with one BFS per
node - `O(N·(N+E))`. Fine into the low thousands of nodes; beyond that, condense
strongly-connected components and DP over the resulting DAG.

## The theta-gamma column layer

The reflex arc gave the brain a nervous system. The column layer gives it
**rhythm** - the slow/fast structure of cortical processing. See
`neuroscience.md` for the science.

### Rhythm

`node.rhythm` is the file's git commit count - how fast it beats. Slow = a
master-tending **theta** node; fast = a **gamma** executor. One `git log` pass
yields both the last-commit time (recency) and the commit count (rhythm).

### Masters (theta)

A **master** is a node of high mass and low rhythm - it governs much and
changes rarely. Detection: every sector keeps at least one master (its heaviest
non-field node); on top of that, any node with `webscore >= masterMassMin`
(default 8.5) and rhythm at or below the 60th percentile becomes a master.
Fields are never masters; `config.masters` force-includes. A node with high
webscore but high rhythm is **not** a master - it is a busy high-mass gamma.
webscore alone cannot find a master; rhythm is required.

### Columns and the third direction

A node's `master` is its **nearest** theta upstream (minimum dependency
distance, not maximum mass - nearest balances columns toward the ideal 1 + 8).
A master plus the gamma it governs is a **column**. The third direction:
`modulatedBy` (the theta masters above a node) and `modulates` (for a master,
the gamma below it). `dependsOn`/`dependedOnBy` carry data; modulation carries
rhythm - it is a different axis.

### Amplitude

`webscore` is **mass** - static blast potential. `amplitude` is the live value:
`mass × theta-gain`, where theta-gain rises when the node's master changed
recently and decays to 1 as the master stays quiet. Rank attention by
amplitude; judge blast by mass; classify the layer by rhythm.

### The hard stop

A fault may ripple down a column (theta → gamma). A fault that climbs up - a
gamma node felling its own theta master - must halt. `cascade()` treats every
master as a firebreak: it is recorded when the wave reaches it but never
propagated through. A gamma-origin cascade that reaches a master trips
`hardStop`. Gamma may never set theta's rhythm.

### New fields

Nodes gain `rhythm, isMaster, layer (theta|gamma), master, column,
modulatedBy, modulates, amplitude`. The graph gains `masters[]`, `columns{}`,
`columnSize` (9 - 1 master + 8 legs), and `stats.masterCount` / `columnCount`.
